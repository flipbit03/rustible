# M9: closing the standard-library gap

Ansible's deepest moat is not its language and not its transport. It is that
`pip install ansible-core` puts seventy modules on your disk that cover
almost everything an operator does to a machine, and every tutorial, every
Stack Overflow answer and every LLM's training data is written against them.
`rustible-std` is our `ansible.builtin`. This document measures the distance
between the two, says which parts of that distance are real, and plans the
work that closes the real parts.

The comparison is against **ansible-core 2.18.12**, whose `ansible.builtin`
module set was enumerated from the installed package rather than from the
website, so it is the list and not a recollection of it: 72 files, less
`async_wrapper` (an internal action helper, not a module) and less `systemd`
(an alias of `systemd_service`), leaves **70 public builtin modules**. Three
more that this comparison needs live in `ansible.posix` rather than
`ansible.builtin` — `authorized_key`, `sysctl` and `mount`, the first two of
which `rustible-std` already implements — and are counted here anyway, because
an operator who installs `ansible` gets them and does not know or care which
collection they came from. **Seventy-three modules, then.**

Two things this document refuses to do. It does not treat parity as the goal:
about a third of `ansible.builtin` exists to give YAML the powers of a
programming language, and Rustible has a programming language, so shipping
those would be a regression. And it does not rank the work by Ansible's module
index; it ranks by what an adopter hits on their first afternoon.

## 1. The measurement

Each of the seventy-three placed in one of four buckets.

| bucket | count | meaning |
|---|---|---|
| **A. Not a gap** | 22 | the module exists because YAML is not a language, or because Ansible needs Python on the target. Rust answers it. |
| **B. Shipped** | 16 | `rustible-std` has it today |
| **C. Real gap** | 31 | an operator will miss this. §4 says which of them we build and which we answer with a paragraph of documentation. |
| **D. Out of scope** | 4 | belongs in a collection, or nowhere |

So: **sixteen done, twenty-two that never need doing, four somebody else's,
and thirty-one gaps** — of which §4 plans ops for about two dozen and answers
the remainder (`assemble`, `script`, `tempfile`, `pause`, most of `getent`)
with documentation or a deliberate deferral.

Thirty-one is a smaller number than the raw index suggests, and that is the
first useful finding: the gap is not "fifty modules behind". It is a specific,
finite list, and two thirds of it is three themes.

### Bucket A — not gaps

These are the modules that exist to bolt control flow, variables, structure
and assertions onto YAML, plus the two that exist because Ansible cannot
assume anything about the target.

| module | Rustible's answer |
|---|---|
| `set_fact`, `set_stats` | `let` |
| `debug` | `ctx.log`, `ctx.debug` |
| `assert`, `fail` | `ensure!`, `bail!` (in the prelude) |
| `validate_argument_spec` | types, checked at compile time |
| `include_vars` | `#[rustible::vars]` |
| `import_tasks`, `include_tasks`, `import_role`, `include_role` | a function taking `&mut Ctx` |
| `import_playbook` | a function, or another playbook |
| `group_by`, `add_host` | inventory groups; runtime host selection |
| `meta` (`flush_handlers`, `end_play`, `end_host`) | there are no handlers (vision 6.6); `return Ok(())` |
| `gather_facts`, `setup` | facts are gathered automatically — but see §4.6, the facts are thin |
| `stat` | `sys.stat()` — a call, not a step, because there is no `register` to need |
| `slurp` | `sys.read()` |
| `ping` | the run probes every host before it uploads anything |
| `raw` | exists only because the target may have no Python. Ours needs nothing. |
| `async_status`, `async_wrapper` | see §7 — backgrounding is a capability question, not a module |

`raw` deserves a sentence of its own, because it is the clearest statement of
what Rustible is for. Ansible ships a module whose entire purpose is "do
something on a box too bare to run my other modules". Rustible's binary *is*
the bare case.

### Bucket B — shipped

| Ansible | `rustible-std` |
|---|---|
| `apt` | `apt::{Present, Absent, Latest}` |
| `user` | `user::{Present, Absent, Removed, Existing, Membership}` |
| `group` | `group::{Present, Absent, Removed}` |
| `copy` | `file::Copy` |
| `file` (`directory`, `link`, `absent`, attributes) | `file::{Directory, Symlink, Absent, Attrs}` |
| `lineinfile` | `file::Line` |
| `blockinfile` | `file::Block` |
| `systemd`, `systemd_service`, `service` (on systemd hosts) | `systemd::{Enabled, Disabled, Running, Stopped, Restart, Reload, DaemonReload}` |
| `hostname` | `hostname::Is` |
| `get_url` | `http::Download` |
| `unarchive` | `archive::Extracted` |
| `command`, `shell` | `shell::Command` |
| `fetch` | `ctx.fetch` |
| `ansible.posix.authorized_key` | `ssh::authorized_keys::{Present, Absent}` |
| `ansible.posix.sysctl` | `sysctl::Present` |
| (no builtin equivalent) | `brew::{Present, Absent}` |

Three small holes inside bucket B, each cheap:

- **`file` has no `touch` and no hardlink.** Ansible's `state: touch` and
  `state: hard`. `Copy::from_str("")` is not the same thing: it truncates.
- **`Owner` is numeric only.** `file::Copy(...).owner(0, 0)` where Ansible
  writes `owner: www-data`. The rustdoc tells the author to read the uid off
  a `user::Account` first, which is honest and correct and also the single
  most-repeated friction in a port. An `Owner::named("www-data")` resolving
  through `/etc/passwd` at check time removes it without weakening the rule.
- **`apt` cannot manage a repository**, which is listed under §4.1 because it
  belongs with the package-manager work.

### Bucket D — out of scope

`subversion` (build it if someone asks twice), `expect` (needs a pty; a
collection), `dpkg_selections` (package holds; folds into §4.1 if wanted),
`pip` (see §4.1 — language package managers are collection material).

## 2. The moat is wider than the module index

Counting modules undercounts the thing the question is actually about. What
ships with Ansible also includes:

- **~150 Jinja filters and tests** (`to_json`, `regex_replace`, `combine`,
  `difference`, `password_hash`, `ipaddr`…). Rustible's answer is the whole of
  crates.io, called from a language with types. This is not a gap; it is our
  strongest counter-moat and it is undersold in the docs.
- **~40 lookup plugins** (`file`, `env`, `pipe`, `url`, `password`, `csvfile`,
  `dig`, `vault`). `rustible-github` is the pattern; `std::env::var` is the
  rest. Not a gap, but worth a named page.
- **Connection plugins.** Ansible ships `ssh`, `local`, `docker`, `podman`,
  `chroot`, `kubectl`, `winrm`, `buildah`. Rustible has `ssh` and `local`. A
  `docker exec` transport is the one that would earn its keep (building images,
  testing our own harness), and it is CLI work, not `rustible-std` work.
- **Ansible Vault.** Encrypted variables at rest, with `ansible-vault` to edit
  them. `rustible-sdk` has `Secret` for in-memory handling and
  `ctx.local_secret` for streaming one to the target, but nothing encrypts a
  file in the repository. For an adopter with a `group_vars/all/vault.yml`,
  this is a migration blocker, and it is not a module.
- **Output formats.** Ansible has callback plugins: `json`, `junit`, `yaml`,
  `minimal`. Rustible renders one human format. A `--format json` is what CI
  and dashboards need.
- **Dynamic inventory.** `aws_ec2`, `gcp_compute`, `k8s`, plus arbitrary
  scripts. Rustible reads KDL. A "shell out to a program that prints the
  inventory" hook is a small feature with a large reach.

None of those five belongs in `rustible-std`. All five belong in the same
conversation, so they are recorded here and then left alone: this document
plans `rustible-std`, and §8 lists the rest as follow-on work.

## 3. Where the real gaps cluster

The twenty-six are not twenty-six independent problems. They are five themes
and a tail.

| theme | modules | why it matters |
|---|---|---|
| **Package managers other than apt** | `dnf`, `dnf5`, `package`, `package_facts`, `apt_repository`, `deb822_repository`, `apt_key`, `yum_repository`, `rpm_key`, plus `apk`, `pacman`, `zypper` which have no builtin module because Ansible keeps them in `community.general` | Rustible cannot install a package on Fedora, RHEL, Rocky, Alma, Amazon Linux, Alpine, Arch or SUSE. `Facts::package_managers` already enumerates six package managers; two have ops. The container tier *already runs `alpine:3.20`* and cannot install anything on it. |
| **Service managers other than systemd** | `service`, `sysvinit`, `service_facts` | Rustible declares macOS a supported target and has no way to manage a launchd job on it. Alpine, likewise, with OpenRC. |
| **Generating file content** | `template`, `replace`, `assemble`, `find`, `tempfile` | Every Ansible repository has `.j2` files. This is the first thing a port hits. |
| **Talking to the network** | `uri`, `git`, `known_hosts` | `http::Download` is GET-to-a-file. A playbook that registers a node with an API, or deploys code from a repository, has nothing. |
| **Touching the host** | `cron`, `mount`, `iptables`, `reboot`, `wait_for`, `wait_for_connection`, `getent` | `wait_for` in particular: "start postgres, then wait until it accepts connections" has no answer today. |
| tail | `debconf`, `script`, `pause` | |

And one that is not a module at all:

- **Facts are thin.** `Facts` has twelve fields. Ansible's `setup` returns
  several hundred, and playbooks branch on them constantly:
  `ansible_default_ipv4.address`, `ansible_interfaces`, `ansible_mounts`,
  `ansible_virtualization_type`, `ansible_selinux`, `ansible_devices`,
  `ansible_processor`, `ansible_env`. A port that needs the host's primary IP
  address — and many do — stops.

## 4. The plan

Six phases. Each is independently mergeable and each leaves the tree green.
They are ordered by what an adopter hits first, not by size.

Every op in every phase ships the checklist in `docs/06_BUILD_PLAN.md` §4:
one type per desired state, `check` doing the thinking and producing the
`Diff`, `apply` executing that diff, an honest prediction or none, refusal by
name on the wrong platform, all I/O through `sys`, rustdoc naming the Ansible
equivalent, pure tests, `Fake` tests, and a container test doing
changed-then-ok. §5 says which of them additionally need tier 4 and why.

### M9.0 — the tiers the rest of the plan needs

Nothing below can be tested honestly until this lands, so it lands first.

1. **RPM-family container images.** Add `fedora:41` and `rockylinux:9` to the
   harness image list. `dnf` inside a stock container works, which is why this
   is cheap and why most of §4.1 can be a tier-3 story.
2. **A systemd RPM image.** `jrei/systemd-*` publishes Debian and Ubuntu only.
   Spike what plays the same role for Fedora — most likely `fedora:41` booted
   with `/usr/sbin/init` under the flags the harness already passes — and if
   nothing works, say so in `DECISIONS.md` and push the RPM service tests to
   tier 4 rather than faking them.
3. **A second machine-tier distribution.** `dev/vagrant/` is two Debian 12
   guests. §4.1 and §4.2 need an RPM guest with a real `dnf` and a real
   systemd, and `CLAUDE.md`'s job-naming rule already anticipates this: the
   distro is matrix data, so the pair becomes `Test: VM (Fedora 41/x86_64)`
   and `(Fedora 41/aarch64)`. Note the libvirt constraint: one architecture at
   a time, per checkout.
4. **macOS as a service-managed target.** No new machinery — the macOS CI job
   already runs playbooks against the runner itself, which is exactly the
   tier-4-equivalent a `launchd` op needs. §4.2 extends that job rather than
   adding one.

Deliberately *not* in M9.0: Arch and openSUSE guests. `pacman` and `zypper`
are §4.1's stretch, and buying two more VM pairs for them before anyone asks
is the wrong trade.

### M9.1 — packages beyond apt

The largest single gap, and the one that decides whether Rustible manages half
of Linux or a quarter of it.

| op | notes |
|---|---|
| `dnf::{Present, Absent, Latest}` | mirrors `apt`'s three-state shape exactly, including `Latest` reading candidates from the metadata. `dnf` and `dnf5` differ in CLI surface; probe and adapt rather than shipping two modules. |
| `apk::{Present, Absent, Latest}` | Alpine. Cheap: the container tier already runs `alpine:3.20`, so this is nearly free coverage. |
| `package::{Present, Absent, Latest}` | the portable op, dispatching on `Facts::package_managers`. This is `ansible.builtin.package`, and it is what makes a cross-distro playbook possible. It must refuse — by name, with the list of what it found — rather than guessing when a host has two. |
| `apt::Repository`, `dnf::Repository` | deb822 (`.sources`) for apt, `.repo` files for dnf, keyring file handling in both. This is `apt_repository` + `deb822_repository` + `apt_key` + `yum_repository` + `rpm_key` collapsed into two ops, because the modern answer to all five is "write a file with a key next to it". Nothing third-party installs — Docker, Tailscale, PostgreSQL, Grafana — without this. |
| `pacman`, `zypper` | stretch. Build when someone asks, not before. |
| `dnf::Present` on a `dnf5` host | verify at tier 3 on `fedora:41`, which ships dnf5. |

**`pip` is not built at all** — not here, not as a collection (§6.4, decided).
Ansible has it in builtin because Ansible is written in Python. Rustible has no
reason to privilege one language's package manager, and `shell::Command`
covers anyone who needs it today.

Also out: `debconf`. It is real and it is needed for unattended installs of a
handful of packages, but it is apt-only and small, and it should follow the
repository ops rather than compete with them.

### M9.2 — services beyond systemd

| op | notes |
|---|---|
| `service::{Enabled, Disabled, Running, Stopped, Restart, Reload}` | the portable op over `Facts::init`, dispatching to systemd, OpenRC or launchd. Same rule as `package`: refuse by name on an init it does not know. |
| `openrc::*` | Alpine, Gentoo. `rc-update`, `rc-service`. |
| `launchd::*` | macOS. `launchctl bootstrap`/`bootout`, plists under `/Library/LaunchDaemons`. **This closes a hole we currently have in the other direction**: the platform table says Rustible manages macOS, and there is no way to manage a service there. |
| a `service_facts` equivalent | as a lookup op returning a typed list, in the shape of `user::Existing`. |

`sysvinit` is folded into `service` as a fallback and gets no op of its own.

### M9.3 — generating file content

The phase an Ansible refugee feels first. `DECISIONS.md` (2026-09-11) records
the current answer — the guide shows `format!`, `include_str!` and
`cargo add` a template crate — and that answer is correct for a config file
with two variables and inadequate for a 200-line `nginx.conf.j2`.

| op | notes |
|---|---|
| `file::Template` | `askama`, compile-time, per §6.1 (decided). The op itself takes the *rendered* string plus the usual file metadata, so `rustible-std` depends on no template engine and the playbook's own `Cargo.toml` carries askama. Note the tax §6.1 names: a `.j2` file does not port verbatim. |
| `file::Replace` | `ansible.builtin.replace`: regex, replace every match. Named in vision 6.9's wave two. Small, pure planning logic, an easy first op for a new contributor. |
| `file::Touch` | plus hardlink support, closing the §1 hole in `file`. |
| `Owner::named` | resolve a user or group name through `/etc/passwd` and `/etc/group` at check time, closing the second §1 hole. |
| `file::Find` | `ansible.builtin.find`: walk, filter by glob/age/size/type, return the paths. A lookup op, never changed. |
| `file::TempDir` | vision §7.3 left this open and the standing recommendation was not to build it. Revisit *only* if `Find` or `Template` turns out to want one; otherwise leave it closed. |

`assemble` — concatenate a directory of fragments into one file — is a
five-line composition of `Find` and `Copy` in a playbook. Document it in the
migration page rather than shipping an op.

### M9.4 — the network

| op | notes |
|---|---|
| `http::Request` | `ansible.builtin.uri`. Methods, headers, a body, JSON in and out, status-code assertions, and a typed response. Shares `http::Download`'s TLS and its URL validation. Note vision 5.1: this runs **on the target**, so it needs egress from there. |
| `git::{Cloned, AtRevision}` | gated on the `gix` spike (§6.2): lock delta, binary delta, and a clean build for all four target triples through the real `cargo_zigbuild` pipeline. Shell out to `git` if any of those fail. |
| `ssh::known_hosts::{Present, Absent}` | belongs next to `authorized_keys` and shares its parsing shape. Required by anything cloning over SSH, which is why it is in this phase and not the tail. |

### M9.5 — the host

| op | notes |
|---|---|
| `wait_for::{Port, Path, Absent}` | pure Rust on the target, no tool to drive, and it answers "started postgres, now wait until it listens". High value per line of code; consider promoting it ahead of M9.4. |
| `cron::{Present, Absent}` | crontab entries with Ansible's marker-comment identity, which `file::Block` has already taught us. A systemd-timer op is the better answer on systemd hosts and is a separate, later question. |
| `mount::{Mounted, Absent}` | `/etc/fstab` plus the live mount. `ansible.posix.mount`. Genuinely tier 4: a container cannot mount. |
| `iptables::{Rule, Chain}` | `ansible.builtin.iptables`, per §6.3 (decided). On Debian 11+/RHEL 8+ the `iptables` command is `iptables-nft`, so this writes nftables rules through the interface everyone already knows. Tier 4: netfilter belongs to the host, so a container cannot test it. |
| `getent` | mostly already covered by `user::Existing` and the group lookups. Fill the rest (services, hosts) only if a port needs it. |
| `script` | ship a local file to the target and run it: `ctx.local_file` + `shell::Command`, already possible. Document, do not build. |
| `pause` | needs the operator's terminal, and the playbook runs on the target. Protocol work for a low-value module; defer. |
| `reboot`, `wait_for_connection` | **architectural, not an op — see §7.** |

### M9.6 — facts

Not modules, but the thing that silently stops ports. Extend `Facts` with what
playbooks actually branch on, each behind a probe that degrades to absent
rather than failing:

- network: interfaces, their addresses, the default route's address and
  interface (`ansible_default_ipv4`, the single most-used fact after `os_family`)
- storage: mounts and their filesystems; block devices
- platform: virtualization type and role (kvm/docker/lxc/none), which the
  container tier makes easy to test
- security: SELinux and AppArmor state
- time and uptime

Each is a pure parsing function over a file or a command's output, so the bulk
of this phase is tier 1, with tier 3 confirming the parse against real
distributions and tier 4 confirming it against a real kernel.

## 5. Testing, tier by tier

The rule in `CLAUDE.md` stands: the lowest tier that can fail for the right
reason. What that means concretely for this plan:

**Tier 1 carries more of this plan than of M6.** Repository files, `.repo` and
`.sources` syntax, crontab lines, fstab lines, template rendering, every facts
parser, `find`'s filters, `known_hosts` parsing — all of it is text in, text
out, and belongs in the op's own file under `// ---- pure ----`.

**Tier 2 is where the `Fake`'s command weakness bites this plan hard.**
`Fake::spawn` returns the first canned entry matching the program and
`with_cmd` consumes `self`, so an op that reads its state with a command
cannot express changed-then-ok at tier 2 at all. `dnf`, `apk`, `openrc` and
`launchd` are all command-driven. Two consequences, both deliberate:

1. Where an op can read its state from a *file* — `cron` via the crontab,
   `mount` via `/etc/fstab`, repositories via their `.repo`/`.sources` files —
   **it must**, because that is the more testable design and `sysctl.rs`
   already shows the pattern for driving the second answer through the
   `Backend` trait.
2. Where it genuinely cannot — `dnf`'s installed set — tier 2 covers
   satisfied, change, apply, refusal and wrong-platform, and changed-then-ok
   is tier 3's job. Say so in the test module rather than writing a test that
   cannot fail.

There is a third option worth costing before the phase starts: **teach `Fake`
a command queue**, so a program can answer differently on successive calls.
That is SDK work, it unblocks changed-then-ok at tier 2 for every
command-driven op in this plan, and it is about a day. Recommended, as M9.0's
fifth item, but recorded as a recommendation rather than assumed.

**Tier 3 grows from five images to seven or eight** and is where §4.1 mostly
lives. Each new test file is another musl build, so add cases to one file per
op rather than a file per case — `it_dnf.rs`, not `it_dnf_present.rs` plus two
siblings. `RUSTIBLE_INTEGRATION_IMAGES` narrows a run while iterating.

**Tier 4 is needed by a specific, short list**, and every other op in this plan
should say in its pull request that it is not on it:

| op | why a container cannot |
|---|---|
| `service::*` / `openrc::*` | a real init as pid 1 — partly reachable with the systemd images, not at all for OpenRC |
| `launchd::*` | macOS; covered by the existing macOS CI job against the runner itself |
| `mount::*` | mounting requires privileges a container does not have, and `/etc/fstab` in a container is a lie |
| `firewall` | netfilter is the host's, shared by the container |
| `dnf::*` on a systemd host | if M9.0's item 2 finds no usable systemd RPM image |
| `reboot` | self-evidently |
| facts: virtualization, mounts, block devices, default route | a container's answers are the host's, which is the bug, not the test |

The tier-4 playbook grows as those land. `examples/workspace/playbooks/` gains
a second playbook for the RPM guest rather than branching inside
`vagrant.rs` on the distro — one playbook per guest family keeps the "second
run reports nothing changed" assertion readable. `make vm-test` runs both.

## 6. Decisions

Four, **all decided by Cadu on 2026-09-14**. Recorded here with the reasoning
so nobody re-derives them; each gets its `DECISIONS.md` entry when the phase
that needs it starts.

**6.1 The template engine: `askama`. DECIDED.** Compile-time, as vision 5.6
already sketched, so a template error is a build error on the operator's
machine rather than a step failure on a target at 2am, and the playbook binary
stays self-contained with nothing to render at run time. Cadu's reason: "look
into the future" — Jinja2 compatibility is a migration convenience that
depreciates, while compile-time checking is a property that does not.

The cost is stated plainly rather than hidden: askama's syntax is Jinja-*like*,
so **an existing `.j2` file does not port verbatim**. Filters differ, `{% for %}`
takes typed values, and anything clever in a Jinja template is a rewrite. That
is a real tax on an adopter with fifty templates, and `docs/ANSIBLE_MIGRATION.md`
(§8.5) owes them an honest page on it rather than a claim that templates "just
work".

The op stays small regardless: `file::Template` takes the rendered string plus
the file metadata every other file op takes (dest, mode, owner, backup, diff),
so `rustible-std` does not depend on askama — the *playbook* does, through its
own `Cargo.toml` and `#[derive(Template)]`. A workspace that wants minijinja
for a tricky legacy template can still use it; the op cannot tell.

**6.2 `git`: spike first, no commitment. DECIDED.** Cadu's concerns, which are
the right ones and which the spike must answer before a line of op code is
written:

1. **Dependency weight.** `gix` is a facade over ~40 crates. Measure the lock
   growth and the binary growth against the current baseline. Every playbook
   that imports the op pays it, on every target.
2. **Cross-architecture builds.** This is the sharper risk. Every playbook
   binary is built through `cargo_zigbuild` against musl and Mach-O targets,
   x86_64 and aarch64. A dependency that pulls C, assumes glibc, or has a
   build script zig cannot drive **breaks the property the project exists to
   have** — and it would break it for every workspace, not just ones using
   `git`. `zlib-ng` and `libgit2` shaped crates are the specific hazard.

The spike ships a measurement, not an opinion: build a trivial playbook
depending on `gix` for all four target triples through the real pipeline, and
report lock delta, binary delta, and whether anything wanted a C compiler that
was not zig. If it passes, `gix` wins on the merit that a target with no `git`
installed can still be deployed to. If it does not, the op shells out to `git`
like Ansible does and says so in its rustdoc. Either answer is acceptable;
guessing is not. Write it up as `docs/plan/reports/GIX-SPIKE.md`.

**6.3 The firewall op: `iptables`. DECIDED.** Cadu's rule: build what Ansible's
standard library builds. `ansible.builtin.iptables` is the module; nftables has
no builtin module at all (it is `community.general`), so shipping nftables
first would be inventing a surface rather than closing a gap.

A correction to the framing that produced this question, because it made the
choice look worse than it is: on Debian 11+, RHEL 8+ and Fedora, the `iptables`
command **is** `iptables-nft` — the nft backend behind the iptables interface,
selected through `update-alternatives`. So building the iptables interface is
not building a legacy path on those hosts; it is writing nftables rules through
the interface everyone's muscle memory and every existing playbook already use.
The vision 6.9 wave-two entry stands as written, and no amendment is needed.

**6.4 `pip`: not built, anywhere. DECIDED.** Not in `rustible-std`, and not as
a collection either — Cadu went further than the recommendation.
`ansible.builtin.pip` is an accident of Ansible being written in Python, and
Rustible has no reason to privilege one language's package manager over
`npm`, `gem`, `cargo` or `go install`. Anyone who needs one writes
`shell::Command`, or writes the collection themselves — which is what
collections are for, and `rustible-github` is the worked example of how.
Bucket D in §1 keeps it, and §4.1 no longer mentions it.


## 7. Two things that are not ops

**`reboot` and `wait_for_connection` are architectural.** The playbook binary
runs *on* the target (vision 5.1), so a reboot kills the thing issuing it.
Making this work means the controller notices the connection drop, distinguishes
an intentional reboot from a failure, waits, reconnects, re-uploads or finds
its binary, and resumes the playbook *at the step after the reboot* — which
means resumable execution, which Rustible does not have and which is a much
larger idea than a module. It is real (kernel upgrades, `/etc/hosts` changes
that need a restart) and it should be a spike of its own, after M9, with its
own document.

**Backgrounding (`async`/`poll`/`async_status`) is the same shape.** Ansible
needs it because a task blocks the controller; Rustible's step blocks a binary
already running on the target, which is a milder problem. Defer, and revisit
only if a real playbook stalls on it.

## 8. Follow-on, outside `rustible-std`

Recorded here so they are not lost, and planned elsewhere:

1. **Encrypted variables at rest** — the Ansible Vault equivalent. A migration
   blocker for anyone with a `vault.yml`, and the one item on this list that
   should probably be scheduled alongside M9 rather than after it.
2. **`--format json`** on the run output, for CI and dashboards.
3. **A `docker exec` transport**, which also makes our own container tier
   testable through the real pipeline instead of a bespoke harness.
4. **Dynamic inventory**: a hook that runs a program and reads the inventory
   from its output.
5. **`docs/ANSIBLE_MIGRATION.md`** — every one of the seventy-two modules, with
   its Rustible answer *including the twenty-three whose answer is "Rust"*.
   This is cheap, it is mostly written above, and the perception gap it closes
   is as wide as the real one: an evaluator who greps our docs for `template`
   and `dnf` and finds nothing concludes we have twenty ops, not that we have
   a language.

## 9. Sequencing

The phases in the order that serves an adopter, with the two forks that can
run in parallel marked:

```
M9.0  tiers        (RPM images, RPM guest pair, Fake command queue, gix spike)
  |
  +-- M9.1  packages beyond apt      ----+
  |     (dnf, apk, package, repos)       |
  |                                      +-- M9.2  services beyond systemd
  +-- M9.3  content                 -----+       (service, openrc, launchd)
        (Template, Replace, Find,
         Touch, Owner::named)
                |
                +-- M9.5  host       (wait_for, cron, mount, firewall)
                |
                +-- M9.4  network    (uri, git, known_hosts)
                        |
                        +-- M9.6  facts
```

M9.3's `Replace`, `Touch` and `Owner::named` are small enough to land before
M9.0 if someone wants an easy start; nothing in them needs a new image or a
new guest.
