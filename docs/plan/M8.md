# M8: `rustup + zig`

**Governing sections:** 5.3 (the dependency rule), 3.
**Depends on:** the macOS spike, `docs/plan/reports/MACOS-TARGET-SPIKE.md`,
whose §10 work is independent of this and stands either way.
**Branch:** `feat/macos-spike` (built there, on top of the spike, 2026-09-13)
**Status:** BUILT. Everything below was done; the deviations from the plan
are listed first, each with the checkpoint that forced it.

## What the build changed about the plan

- **Two things step 2's checkpoint found that the plan had not.** Build
  scripts and proc-macros link with the *host* linker, which cargo-zigbuild
  never wires (and actively un-wires when host == target), so
  `wire_host_linker` sets `CARGO_TARGET_<HOST>_LINKER` to zig; and `ar`,
  `lib`, `install_name_tool` are symlinks to the current executable
  dispatched on `argv[0]`, so `main` starts with `dispatch_as_tool`.
- **`toolchain check` stays**, rewritten on zig: CI's cross-builds have no
  other way, and `--print-env` is how to give rust-analyzer the zig
  `rustible` uses. It also exports `CARGO_ZIGBUILD_ZIG_COMMAND`, which the
  `ar` symlink needs and nothing else supplies.
- **The container-tier harness keeps the host's C compiler.** It lives in
  `rustible-sdk`, which every playbook links; a developer requirement, like
  docker.
- **Provisioning is gated by a preflight**, not just by the subcommand: a
  unit test running the real binary with `--inventory nope.kdl` downloaded
  476 MB before `dispatch` could refuse it. `needs_zig` now also requires the
  flags to be acceptable and the named inventory to exist.
- **Known gap, recorded in DECISIONS:** a plain `cargo build` or
  rust-analyzer in a playbook workspace still needs a system `cc` for
  `ring`'s build script; `eval "$(rustible toolchain check --print-env)"`
  is the way round it.
- **Cosmetic, left alone:** a Darwin build from a non-mac prints rustc's own
  `warning: invoking "xcrun" ... failed` once, because rustc goes looking for
  an Apple SDK it does not need under zig. Pointing `SDKROOT` at an empty
  directory was tried and produces two warnings instead of one, so it is
  not silenced; the build is unaffected and the binary runs.

## Why this milestone exists

It started as "can Rustible manage a mac", and it is here because the answer
turned out to be about the build system rather than about macOS.

**The macOS question was answered, and cheaply.** The spike shipped a playbook
to a real mac from both a Linux and a macOS controller, escalated through the
mac's own `sudo`, did TLS from the target, and reported changed→ok. It took 209
lines. The Mach-O linker was `rust-lld`, already inside rustup; nothing new was
installed.

**Except for one thing.** Cross-compiling from Linux needs Apple's `.tbd` link
stubs for `-lSystem` and Apple's headers for `ring`, and Apple's SDK is not
redistributable. So the spike's instructions contained the sentence "copy the
SDK from a mac you own". Cadu's verdict: *"this is not good imho, super
sketchy… this is terrible DX"*. He was right, and it was the only part of the
whole spike that added anything to the dependency rule.

**The first answer was to retreat.** Support macOS targets only from a macOS
controller: no SDK, no new dependency, and a rule statable in one sentence. It
costs almost nothing, because a macOS controller already manages Linux hosts,
so one mac drives the whole fleet.

**The second answer was to ask a question nobody had measured.** Cadu asked
whether `cargo-zigbuild` could substitute for clang. Reading
`docs/plan/reports/C-TOOLCHAIN-SPIKE.md` back, its governing question was
literally *"Can `ring` build for both musl targets with rustup + clang + musl
headers, no gcc cross-toolchain, **no zig**?"* — zig had been excluded by the
rule and never tested against it. So the measurement had never been taken.

**Taking it inverted the conclusion.** zig serves every target Rustible has,
plus FreeBSD and NetBSD, carrying its own libc for each. The Apple SDK problem
disappears. And so do the vendored musl headers, the compiler-selection matrix,
the `--sysroot` dance for `x86_64-musl`, and the `-idirafter` workaround for
Apple clang's patched `stddef.h`.

**That is the trampoline.** The SDK was a symptom. The condition is that
Rustible maintains a *matrix* — which compiler serves which target, with a
different answer per target, per host OS, and per compiler vendor — and
`toolchain.rs` is 999 lines of exactly that. macOS did not create the problem;
it was just the first target where the matrix ran out of road, because there
was no way to paper over a missing Apple SDK the way musl's missing headers had
been papered over by vendoring them into the repository.

**And the rule had already evolved once, the same way.** Vision 5.3 records
that the original rule forbade C outright and that `cargo-zigbuild` was
"considered as an escape hatch and dropped" — then records that the rule was
narrowed when `rustls-graviola` aborted on a real host below Broadwell and
`ring` was measured to be better. The lesson there was that *the rule was
protecting the toolchain, not the language*. This is the same lesson a second
time: the rule names zig as forbidden in order to protect the toolchain from
sprawl, and measurement says zig **reduces** the sprawl by about 1,200 lines.
The letter of the rule and its intent had come apart again.

So: the milestone is not "add macOS support". It is "stop maintaining a
compiler matrix", and macOS support falls out of it for free.

## What was measured

On `feat/macos-spike`, 2026-09-12/13. zig 0.15.2, cargo-zigbuild 0.23.4, no
clang environment, no SDK.

| target | result |
|---|---|
| `aarch64-apple-darwin` | 686,208 B — **ran on `cadumac`** |
| `x86_64-unknown-linux-musl` | 851,000 B, static — ran here |
| `aarch64-unknown-linux-musl` | 778,352 B, static |
| `x86_64-unknown-freebsd` | built; not run, no FreeBSD host |
| `x86_64-unknown-linux-gnu`, **`CC=/bin/false`** | built **and linked** |

The last row is the one that matters: with an explicit `--target`, zig serves
the compile *and* the link, so no system C compiler is needed at all.

**Without `--target` it does not.** Measured separately: `CC=/bin/false cargo
zigbuild` with no target fails inside ring's build script, having invoked
`/bin/false` rather than zig — cargo-zigbuild only installs its wrappers for
an explicit target. So "zig fulfils everything" is true *given* step 2 below,
and false without it.

Binary size is a wash — the same playbook for `aarch64-apple-darwin` is
689,952 B through clang+SDK and 686,208 B through zig. zig's linker ad-hoc
signs Mach-O, which arm64 macOS requires.

zig ships libc for **96 triples**: glibc 14, musl 12, netbsd 12, freebsd 6,
macos 2, windows-gnu 4, wasi. No OpenBSD, no illumos/Solaris. It runs on 23
host platforms.

**`cargo-zigbuild` is a library** — `cargo_zigbuild::{Build, Zig}` are public —
so it is a crate dependency of `rustible-cli`, not a program the operator
installs.

## How zig gets onto the machine (DECIDED)

`Zig::find_zig()` searches `python -m ziglang`, then `zig` on `PATH`. It never
downloads. Someone has to put zig on the machine:

1. **The operator installs it.** Rule: `rustup + zig`. But zig is not in most
   distro repositories at a usable version, so in practice it is a 51 MB
   tarball from ziglang.org; on Cadu's own box `pip` does not exist and
   `python3 -m venv` has no `ensurepip`, so the documented pip route was
   unavailable. Legitimate — a vendor download, checksummable — but manual.
2. **Rustible fetches a pinned zig** into the workspace cache, checksum
   verified, once per machine. The same shape as
   `unpack_x86_64_musl_headers` → `<cache>/musl-headers/<version>-x86_64`,
   fetched rather than embedded because 380 MB cannot live in the repository.
   The operator then installs nothing but rustup, which is **less than today**.
3. **Both**: use zig if present, else fetch, plus `rustible toolchain install`.

**Cadu chose 3, 2026-09-13.** It is the only option where the dependency rule
shrinks rather than moves sideways, and "the controller needs nothing but
rustup" is the same promise the project already makes about targets.

What that commits this milestone to:

- **An operator's zig always wins.** `zig` on `PATH`, or `python -m ziglang`,
  or `RUSTIBLE_ZIG` pointing at one, is used as-is and never second-guessed —
  the same rule the old module had for a `CC_<triple>` already in the
  environment.
- **Otherwise Rustible provisions one**, pinned by version and checksum, once
  per *machine*. The download is announced, not silent, exactly as
  `ensure_targets_installed` announces a `rustup target add`.
- **It goes somewhere Rustible owns, and nowhere else.**
  `$XDG_CACHE_HOME/rustible/zig/<version>/`, falling back to
  `$HOME/.cache/rustible/zig/<version>/` — which is already the project's
  convention, since the *remote* binary cache on every target is
  `$HOME/.cache/rustible/bin/`.

  Note this is deliberately **not** `Workspace::cache_dir()`, which is
  `root.join(config.cache_dir)` and therefore workspace-local. That was right
  for 1.2 MB of vendored musl headers and is wrong for a 380 MB toolchain:
  five workspaces would mean five copies. zig is a property of the machine,
  not of the workspace.

  The non-goals are as firm as the goal. Rustible **never** edits `PATH`,
  never writes to a shell rc, never installs to `/usr/local` or any system
  directory, never creates symlinks outside its own cache, and never asks for
  elevation on the controller. zig is invoked by absolute path and is
  invisible to everything else on the machine. The directory is versioned, so
  bumping the pin installs alongside rather than over, and deleting the whole
  tree is always safe: the next build re-fetches it. That is the entire
  contract, and it is the same one the project already makes about targets —
  solve our case portably, leave the machine as we found it.
- **`rustible toolchain install`** does it deliberately and ahead of time, so
  a first `playbook run` need not be the thing that pulls 380 MB, and so an
  air-gapped machine can be primed from elsewhere. This is the subcommand that
  replaces `toolchain check`, whose reason for existing goes away with the
  matrix.
- **A refusal, not a guess, when provisioning is impossible**: no network and
  no zig has to name `RUSTIBLE_ZIG` and the pinned version, rather than failing
  somewhere inside cargo.

Steps 1-2 below are unaffected by this and come first regardless.

## Steps, in the order that fails soonest

1. **Wire `cargo_zigbuild::Build` into `Cargo::build`**, behind the existing
   `env_for_build` seam, zig found on `PATH` only. Delete nothing yet.
   *Checkpoint:* `make` green; a playbook built and run against the ARM VM and
   against `cadumac`, both changed→ok. First proof end to end rather than by
   `--describe`. **Abandon cheaply here if the library API disappoints.**
2. **Pass `--target` for the host describe build.** This step is what makes
   "no clang" true, and it is not optional — **measured 2026-09-13**: with no
   `--target`, cargo-zigbuild does not intercept the C compiler at all, and
   `CC=/bin/false cargo zigbuild` dies in ring's build script using
   `/bin/false`. With an explicit host triple the same command builds and
   links. The describe build is today the only build with no `--target`, so
   it is today the only one that would still need a system `cc`.
   Two consequences for the code: `Cargo::debug_bin()` is
   `target_dir/debug/<bin>` and must become `target_dir/<host triple>/debug/
   <bin>`, and the host triple has to be discovered (`rustc -vV`).
   *Checkpoint:* `--describe` and `--check-vars` work under `CC=/bin/false`,
   with no clang and no `cc` reachable.
3. **Implement provisioning** (option 3 above): locate-or-fetch via `curl`,
   the hardcoded pin and its SHA-256, pure-Rust unpack with `tar` +
   `lzma-rust2`, `RUSTIBLE_ZIG`, and `rustible toolchain install`.
   *Checkpoint:* a machine with neither zig nor clang builds and ships a
   playbook; and one with `RUSTIBLE_ZIG` set never touches the network.
4. **Delete.** `toolchain.rs` body (999), `toolchain_cmd.rs` (139),
   `build.rs` (67), `vendor/musl-headers/` (1.2 MB), the musl stanzas in
   `templates/cargo-config.toml`, and the clang advice in `rustible init`
   (`Compilers::probe`, `init_warning`, `build_failure_hint`).
   *Checkpoint:* `make` green; no test assertion changes except those naming
   clang or the musl headers.
5. **CI, all eight jobs, plus `release.yml`.** Each needs zig. The macOS job
   asserts `clang --version` and cross-builds "with Apple clang and the musl
   headers the CLI carries" — that step's premise is gone. `release.yml`
   builds `rustible-cli` itself for three targets with plain `cargo build`
   and `rust-lld`, and keeps doing so: the CLI stays pure Rust, so it needs no
   zig to build. Add a `Build: FreeBSD cross` job, now nearly free, to guard the
   claim.
6. **Rules and docs**, below.
7. **Re-verify the macOS work**: `mac.rs`, `macdeep.rs`, `macbrew.rs` all
   changed→ok, built through zig.

## How the CLI fetches zig without gaining a C dependency (DECIDED)

Found while vetting this plan. `rustible-cli` today depends on
`rustible-sdk`, `rustible-build`, rustix, serde, anyhow, clap, tokio, openssh,
sha2, kdl, toml, tempfile. **There is no HTTP client and no `ring`**, so
`cargo install rustible-cli` needs *no C compiler at all*; only building a
playbook does.

Downloading a 51 MB `.tar.xz` the obvious way (`ureq` + `rustls` + `ring`)
would put C into the CLI, so installing Rustible would need a C compiler
*before zig exists to be that compiler*. A bootstrap loop, and it would put an
asterisk on the very promise this milestone makes.

**Cadu's answer, 2026-09-13: shell out to `curl`.** The system tool does the
TLS, nothing links `ring`, and a machine without curl is told so plainly rather
than being guessed at.

- **curl alone, not curl-or-wget.** Supporting both was considered and
  dropped: it doubles the download path for a case that barely exists.
  **Anyone who has rustup almost certainly has curl**, because rustup's own
  canonical install is
  `curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh`. macOS
  ships `/usr/bin/curl` in the base system and does not ship wget at all.
  Measured in base *container* images, 2026-09-13: Fedora and Arch carry curl
  and not wget; Debian 12 and Ubuntu 24.04 carry neither (they are stripped
  images, not controllers); **Alpine is the one family that carries busybox
  `wget` and no curl**, so an Alpine controller needs `apk add curl`. That is
  the whole cost of the simplification, and it is acceptable.
- **`tar` is *not* a second system dependency.** The tarball is unpacked in
  pure Rust with the `tar` and `lzma-rust2` crates, both already workspace
  dependencies and both verified C-free (no `build.rs`, no `cc`, no `*-sys`
  in either tree). `rustible-std::archive` already decodes `.tar.xz` with
  exactly this pair, so it is a proven path rather than a new one. `sha2` is
  already a `rustible-cli` dependency, so the checksum needs nothing new
  either.
- **The pin is hardcoded, not discovered.** zig's `download/index.json`
  publishes `tarball`, `shasum` (SHA-256) and `size` per host triple —
  verified:

  ```
  tarball: https://ziglang.org/download/0.15.2/zig-x86_64-linux-0.15.2.tar.xz
  shasum : 02aa270f183da276e5b5920b1dac44a63f1a49e55050ebde3aecc9eb82f93239
  ```

  Those go in the source, one row per supported host triple. Fetching
  `index.json` at run time would be an unpinned network dependency and a
  second download, and would let upstream change what we install.
- **The refusal stays short.** No per-distro install commands: keeping a table
  of how six package managers spell "install curl" is a maintenance burden for
  no benefit, and it rots. The message says curl is missing and is needed to
  download zig, and stops. Note the ordering makes that unambiguous — zig on
  `PATH`, `python -m ziglang`, and `RUSTIBLE_ZIG` are all consulted *before*
  any download is attempted, so this error only ever fires when there is
  neither a zig nor a way to fetch one.

Net: `cargo install rustible-cli` stays C-free, `release.yml` needs no zig for
the CLI itself (it is pure Rust and `rust-lld` still links it), and the
dependency list is **`rustup` + `zig` + `curl`** — where zig is fetched for
you.

Checked while here: `cargo-zigbuild` declares `rust-version = "1.88"`, under
the project's 1.95 floor, so the `Build: MSRV 1.95` job is not at risk.

## Risks

- **zig is pre-1.0 and breaks between releases.** This puts a pre-1.0
  dependency at the centre of the build. zig and cargo-zigbuild are a matched
  pair: pin both, test the pair in CI, treat a bump as its own PR. This is the
  strongest objection and it does not go away.
- **380 MB per dev machine and per CI runner.** Caching helps; first-run does
  not.
- **A pinned zig can lag a new rustc.** Surfaces as a link error at build time,
  not at run time — the survivable direction.
- **cargo-zigbuild's library API is not its headline product.** `Build` is
  `clap`-derived, so driving it in-process means building a CLI-shaped struct.
  Step 1 is where that gets found out.
- **`rustible` will have to answer to `rustible zig cc`.** Found while vetting,
  and concrete. cargo-zigbuild does not set `CC`/linker to zig directly: it
  writes a wrapper shell script per target and points rustc's `-C linker=` at
  it. Verified on this machine:

  ```sh
  # ~/.cache/cargo-zigbuild/0.23.4/wrappers/45fa/zigcc-x86_64-unknown-linux-gnu-8781.sh
  exec "/home/cadu/.cargo/bin/cargo-zigbuild" zig cc -- -target x86_64-linux-gnu "$@"
  ```

  The executable named there comes from `resolve_current_exe()`, which is
  `env::current_exe()`. So when the library is driven from `rustible`, **the
  wrappers will exec `rustible zig cc …`**, and `rustible-cli` must expose a
  (hidden) `zig` subcommand forwarding to `cargo_zigbuild::Zig::execute_compiler`,
  or every build dies with clap's "unrecognized subcommand". Not a blocker —
  the API is public and `CARGO_BIN_EXE_cargo-zigbuild` is an override — but it
  is day-one work, not a detail.
- **cargo-zigbuild keeps its own cache** at `~/.cache/cargo-zigbuild/<version>/`
  (104 KB here, just wrapper scripts). Small and harmless, but it is a second
  directory outside the "Rustible owns its locations" contract above, and the
  docs should say so rather than imply we control everything.
- **Offline builds.** Today a machine with clang builds offline. Under options
  2/3 the first build needs network; `RUSTIBLE_ZIG` must exist for air-gapped
  use.

## Rule amendments

Cadu's to apply. Prose offered, not written to the files.

**`CLAUDE.md`, the dependency rule** — currently "rustup plus `clang` … No
cross-gcc, no zig, no docker for builds":

> **rustup plus zig is the entire set of dependencies for running Rustible, and
> that must never grow.** Target hosts need nothing at all, ever. zig *is* the
> C toolchain: `ring`, the TLS provider, compiles a little C, and zig compiles
> it for every target Rustible ships to — musl, Darwin, and whatever comes
> next — carrying its own libc for each, so there is no SDK to obtain and no
> header set to vendor. `cargo-zigbuild` is a library dependency of
> `rustible-cli`, not a program the operator installs. A crate that bundles a
> C *library* (`openssl-sys`, `libgit2-sys`) remains unsupported; the fix is
> the pure-Rust alternative.

**Vision 5.3** records that `cargo-zigbuild` "was considered as an escape hatch
and dropped" and that macOS targets are deferred for "their own toolchain and
SDK requirements". Both are now falsified by measurement, and the section wants
rewriting around the new rule — including the fact that it was clang, not zig,
that needed the vendored headers and the per-vendor workarounds.

`DECISIONS.md` entries [M7-ring], [M7-macos] and the musl-headers entries
describe machinery that would no longer exist. They stay as history — the file
is append-only — and a new entry supersedes them.

## What this does not change

- The macOS **operation** work from the spike (`Os::Macos`, `Distro::Macos`,
  the `Pm` set, correct facts on a mac, the gate on all 31 ops, `brew`). All
  of it is independent of how a binary is compiled.
- **The target still installs nothing.** Untouched, and the property the
  project exists for.
- `ring`, `rustls`, and the reasons for both.
- The four testing tiers.

## Cost

Steps 1-2: about a day, and they are the ones that prove or kill it. Steps 4-7
are mechanical but wide — eight CI jobs, two rule documents, and a deletion
touching `describe.rs`, `init.rs` and the templates. Three to four days total.

The prize, measured: **~1,200 lines and 1.2 MB of vendored headers deleted**,
one compiler instead of a matrix, macOS targets from any host, FreeBSD nearly
free, and the operator installing less than they do today.
