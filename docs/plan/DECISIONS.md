# Decisions

One line per decision, each with how to reverse it. Append; do not rewrite.
Format: `- [M<n>] <date> <decision>: <why>; <how to reverse>`.

- [M1] 2026-09-08 `rustible init` must generate `[profile.dist]` and `.cargo/config.toml` (rust-lld per musl target) in every workspace: a detached workspace inherits neither from the repo; found when the orchestrator's dist build failed against `examples/workspace`. Reverse: none needed, this is a gap in the M4 brief, not a design change.
- [M1] 2026-09-08 `#[rustible::vars]` rejects maps and tuples syntactically; nested structs cannot be told from enums in a proc macro, so the orchestrator's vars validation (M2/M3) must reject schema properties of `type: object`. Reverse: add a `#[vars]`-side check if a reliable syntactic rule appears.
- [M1] 2026-09-08 `--var k=v` parses `v` as JSON when it parses, else as a string (numbers, bools, lists work without quoting). Reverse: make it string-only and require typed syntax.
- [M1] 2026-09-08 Vars deserialization does NOT use `deny_unknown_fields`: the host var bag is shared by all playbooks targeting the host (vision 10.3), so undeclared keys are legitimate; the runtime warns per undeclared key with a did-you-mean instead. Reverse: add `deny_unknown_fields` in the `#[vars]` expansion.
- [M1] 2026-09-08 Alternating `rustible playbook run` between two playbooks re-links the bin each time (one `selected` OUT_DIR, `rerun-if-env-changed`). Observation for M3: weigh a per-playbook artifact cache keyed by (playbook, triple, source hash) against duplicated dependency artifacts. Reverse: n/a, nothing built.
- [M1] 2026-09-08 `rust-version` raised from 1.85 to 1.88 because the code uses let-chains (stable in 1.88, edition 2024). Reverse: nest the `if let`s.
- [M1] 2026-09-08 Vars flatness is enforced on the generated JSON Schema (`vars::flatness_violations`, resolving `$ref`s) at `--describe` and at `Start`; the macro's syntactic map/tuple rejection is only an early hint. Supersedes the earlier M1 note that deferred this to M2/M3.
- [M4] 2026-09-08 `rustible init` treats a directory holding only `.git` as empty: `git init` before `rustible init` is the common order and vision 10.4 already expects a git repository. Reverse: drop the `.git` exception in `is_empty_dir`.
- [M4] 2026-09-08 `rustible init --name <name>` overrides the package name derived from the directory, and names Cargo refuses (Rust keywords, `test`, `core`, `std`, ...) or that would shadow a dependency (`rustible`, `rustible-std`, ...) are rejected with a message pointing at `--name`: a directory called `type` or `rustible` would otherwise produce a workspace that cannot build. Reverse: remove the flag and the reserved list.
- [M4] 2026-09-08 `.gitignore` lines are `/target` and `/.rustible` (root-anchored, as in `examples/workspace`), and an existing `.gitignore` is appended to whether or not the directory is a git repository (the brief's "inside a git repository" condition only matters when the file exists, and then appending is right either way). Reverse: write `target/` and `.rustible/` and check for `.git` before appending.
- [M4] 2026-09-08 `--path-deps <checkout>` is written into the manifest as given (a relative path is relative to the new workspace, like Cargo's own `path =`), after checking that `<checkout>/crates/{rustible,rustible-std,rustible-build}/Cargo.toml` exist. Reverse: canonicalize to absolute.
- [M4] 2026-09-08 The regeneration test compares `Cargo.toml`, `build.rs`, `src/main.rs` and `.cargo/config.toml` of `examples/workspace` byte for byte, including the version in the shim headers; a version bump therefore requires `rustible init --refresh examples/workspace` (one command, and the test's failure message says so). `src/lib.rs`, `hosts.kdl` and `playbooks/` carry example content and are not compared. Reverse: normalize the version in the test.
- [M4] 2026-09-08 `rustible playbook create` adds `.rs` when the path lacks it, refuses to overwrite an existing file, and warns (but still writes) when the path is outside the workspace's `playbooks/` or outside any workspace, because the build script would not discover it. Reverse: make these errors.
- [M4] 2026-09-08 `--force` keeps existing user-owned files and rewrites only the two shims (review found it overwrote hosts.kdl and src/lib.rs). Reverse: make --force overwrite everything again.
- [M4] 2026-09-08 PROPOSED AMENDMENT for Cadu: `rustible init` refuses any non-empty directory (vision 3); a fresh GitHub clone with README, LICENSE and .gitignore is refused and needs --force. cargo-init-style conflict-based refusal (only when a file init would write already exists) would be friendlier. Not changed; vision doc wins. **DECIDED by Cadu 2026-09-08: adopt the cargo rule.** Implemented on branch `amendments`; see `[M7-amend] init` below.
- [M4] 2026-09-08 Post-init hint prints `cargo run -- hello` with `rustible playbook run` marked "once available", because M3 lands after M4. Reverse: switch the hint when M3 merges (M3 brief should do this).
- [M6-harness] 2026-09-08 Integration tests are opt-in with `RUSTIBLE_INTEGRATION=1` and skip (pass, printing why) without it or without a working `docker`; the brief's "runs in CI when docker is available" becomes "CI sets the variable where docker exists". A plain `cargo test --workspace` never pulls images or builds for musl. Reverse: drop the variable check in `testing::skip_reason` and gate on `docker info` alone.
- [M6-harness] 2026-09-08 The test binary is rebuilt for `<arch>-unknown-linux-musl` in release from inside the running test (`cargo test --no-run --release --target ... --test <file>`, once per process) rather than by an outer wrapper or build script; vision 8.3 wants a static binary and this keeps `cargo test` the only entry point. Consequence: test file names must be valid crate names (underscores). Reverse: a `cargo rustible-test` wrapper that builds first and passes the path in.
- [M6-harness] 2026-09-08 `rustible-std` takes `rustible` as a dev-dependency (a dev-only cycle, the same shape `rustible-macros` already uses) so `tests/` can write `#[rustible::integration_test]` as an op author would. Reverse: re-export the attribute from `rustible-sdk` and drop the dev-dependency.
- [M6-harness] 2026-09-08 The brief's `SystemdImage` variant is `testing::Image::Systemd`, written as `systemd_images = ["..."]` next to `images = [...]` in the attribute (string literals only, so both lists share one syntax). Systemd containers run `--privileged --cgroupns=host` with the host cgroup mounted; the documented images are the third-party `jrei/systemd-debian:12` and `jrei/systemd-ubuntu:24.04` because stock images ship no systemd and installing it per run costs tens of seconds. Reverse: an `images = [systemd("...")]` syntax, or a `Dockerfile` under `crates/rustible-sdk/` that builds our own systemd images.
- [M6-harness] 2026-09-08 In-container detection requires `RUSTIBLE_INTEGRATION_INSIDE` plus `/t`; explicit `RUSTIBLE_INTEGRATION=1` with no docker or an empty image filter is a failure, not a skip. Container bodies run under `timeout 600`; systemd containers have a Drop guard.
- [M6-harness] 2026-09-08 DEFERRED to M7: replace the harness's own Report/StepReport wire format with a replay of `event::Event` via JsonLines (design-quality only).
- [M6-harness] 2026-09-08 Systemd images keep `--cgroupns=host` and the host cgroup bind mount because the jrei images (VOLUME /sys/fs/cgroup) do not boot otherwise; a purpose-built image would allow plain `--privileged`. Reverse: build `rustible/systemd-debian` from six lines and drop both flags.
- [M2] 2026-09-08 Sibling-group conflicts are checked for parameters as well as vars: vision 10.3 decides the rule for vars and 10.2.1 says "nearest group outward" for parameters without saying what a tie means; the same rule keeps `ssh_user` from silently depending on file order. Reverse: skip `ConflictKind::Param` in `check_conflicts`.
- [M2] 2026-09-08 Group distance is the shortest path from the host: the group a host is nested in and every group that lists it in `members` are distance 1, a group listing a distance-d group is d+1, and a group reachable by two paths takes the shorter one. Reverse: change `group_levels`.
- [M2] 2026-09-08 Conflicts are detected at load (every host is resolved in `check_conflicts`, so `inventory check` reports them with the host's line) and `resolve()` re-checks; after a clean load it can only fail on an unknown host. Reverse: drop `check_conflicts` and let `resolve` report.
- [M2] 2026-09-08 `ssh_args` has two spellings because a KDL property holds one value: `ssh_args="-4"` (one string) or a child node `ssh_args "-o" "X"` (the list), and both count as the same parameter for "set twice". Reverse: drop the property form.
- [M2] 2026-09-08 `#null` is rejected in `vars` ("leave a var out instead"), integers must fit i64, lists are positional arguments and may mix scalar types (the schema check reports the type, not the parser). Reverse: map `#null` to an absent key.
- [M2] 2026-09-08 A `group` node lexically inside a `group` is an error pointing at `members` (vision 10.1: groups contain groups through `members`); a host is nested in at most one group by placement (10.2.3) and referenced elsewhere by name. Reverse: allow lexical nesting as sugar for `members`.
- [M2] 2026-09-08 Undeclared vars are warnings, and a schema property of `type: object` is an error, as M1 recorded; `inventory check` validates the file only until M3 wires `--describe`, and the schema-facing API (`validate`, `format_vars_report`) is exercised by tests against a fixture of the M1 `--describe` shape. Reverse: n/a.
- [M2] 2026-09-08 The spike orchestrator's flat flags moved under `rustible run` unchanged (vision 3 is noun-first: `inventory show`, `playbook run`); M3 deletes `run`. Reverse: n/a, temporary.
- [M2] 2026-09-08 `inventory show` prints lists as `[a, b]` and other scalars in KDL 2.0 spelling (`#true`, quoted strings). `[..]` is not KDL (lists are positional arguments there) but reads unambiguously in a table. Reverse: print lists space-separated.
- [M2] 2026-09-08 A single positional var value is a scalar; where the playbook schema wants a list it is coerced to a one-element list on both sides (`vars::coerce_scalars_to_lists`); a var with no values is an empty list. Reverse: add an explicit list syntax and drop the coercion.
- [M2] 2026-09-08 Non-finite floats are refused at parse; integers above i64::MAX are carried as `Scalar::UInt`.
- [M2] 2026-09-08 The built-in `ssh_user` is USER, then LOGNAME, then the uid's /etc/passwd entry, else left to ssh's default (never a `root` guess).
- [M2] 2026-09-08 FOR M3: the orchestrator pre-check validator is a JSON Schema subset; give the `--describe` host build a `--check-vars` mode so serde is the single validator on both sides. Not done in M2.
- [M6] 2026-09-08 `ssh::authorized_keys::Present` (user form) refuses when the user's home directory does not exist instead of creating it root-owned on the way to `~/.ssh` (vision 6.7); `~/.ssh` itself is created because the brief and Ansible's `manage_dir` default ask for it. Reverse: drop the home check in `check_parent`.
- [M6] 2026-09-08 `ssh::authorized_keys`: a requested line that does not parse as a public key fails the step at `check` instead of being appended verbatim, so a playbook typo cannot land in `authorized_keys`. Reverse: append unparseable lines untouched.
- [M6] 2026-09-08 `ssh::authorized_keys`: key identity is `(key_type, key)`; options and comment are ignored for matching and an existing line is never rewritten to match the requested options or comment (Ansible ignores the comment but rewrites options). Reverse: compare options in `same_key` or rewrite the raw line on mismatch.

- [M6-ak] 2026-09-08 A symlinked `authorized_keys` file is refused (atomic rewrite would replace the link); `in_file(real path)` is the workaround. Reverse: resolve the link target and write there.
- [M6-ak] 2026-09-08 User lookup reads `/etc/passwd` only; NSS-only accounts (LDAP, SSSD, systemd-homed) are unsupported by the user-name form, `for_account` covers them. Reverse: route through `getent passwd` via `sys.cmd`.

- [M6-ug] 2026-09-08 `user::Present` and `group::Present` predict their output only when it is honest (vision 12): an existing account or group is always predicted; a new one is predicted only when the uid (gid) is given, and for a user the primary gid must be given explicitly (the earlier private-group `gid == uid` guess was dropped on review: login.defs ranges are not modelled). Otherwise `Plan::change` without a prediction, so a check-mode run that chains from the step stops with the vision's clear message. Reverse: predict with a sentinel and document it.
- [M6-ug] 2026-09-08 `apply` in `user::Present` and `group::Present` executes the `Diff::Attrs` that `check` produced (create when an `exists` change is present, else `Delta::from_changes` for `usermod`) instead of inspecting the system again, then re-reads `/etc/passwd` and `/etc/group` for the real output. Vision 6.2 ("`check` does all the thinking; `apply` executes that diff") and it is what makes the Fake tests able to plant the tool's effect. Reverse: re-run the inspection in `apply`.
- [M6-ug] 2026-09-08 `Present::append` defaults to `true` (Ansible's default is `false`): adding a user to `docker` must not silently drop them from `sudo`; `.append(false)` gives the exact-set semantics. Reverse: flip the default.
- [M6-ug] 2026-09-08 On Alpine (BusyBox) an existing account's uid, gid, home, shell or comment cannot be changed (no `usermod`) and an existing group's gid cannot be changed (no `groupmod`); both fail at `check` naming the `shadow` package. - [M6-ug] 2026-09-08 `Present::gid` takes `impl Into<GroupId>` (a `u32`, a `&str` name, or `&group::Group`); a numeric gid or a name must already exist in `/etc/group` (vision 6.7), as `useradd -g` itself requires. Reverse: accept only `u32`.
- [M6-ug] 2026-09-08 `group::Absent` fails at `check` when the group is some user's primary group (`groupdel` would refuse in `apply` with a less clear message). Reverse: let `groupdel` fail.
- [M6-ug] 2026-09-08 `user::Membership` is satisfied when the group lists the user or is the user's primary group; adds with `usermod -aG` (BusyBox `addgroup user group`), never removes. `Membership::of(&Account)` / `of_name(..)` and `in_group(&Group)` / `in_group_named(..)` both exist so playbooks can chain from ops or use plain names.
- [M6-ug] 2026-09-08 `/etc/passwd` and `/etc/group` are read directly, as the vision plans; NSS-only accounts (LDAP, SSSD, homed) are not seen, same known limitation as `ssh::authorized_keys`. A line that names the requested user or group but does not parse is an error, not "missing".

- [M6-ug] 2026-09-08 `user::Present` with no `.groups(..)` leaves supplementary memberships alone whatever `append` says; an explicit empty set with `.append(false)` strips them. Reverse: treat "no groups" as the empty set again.
- [M6-ug] 2026-09-08 `Tools::of` probes for `usermod`/`useradd` and then `busybox`/`adduser` before falling back to the distro name, so `apk add shadow` on Alpine (and BusyBox-only images of other distros) are handled by what is actually installed. Reverse: decide by distro only.
- [M6-ug] 2026-09-08 A relative or empty home is refused at `check` in `user::Present` and in `ssh::authorized_keys`' passwd lookup: `useradd` accepts a relative `-d` and writes it into passwd verbatim, which later resolves against the caller's cwd. Reverse: pass it through.
- [M6] 2026-09-08 The `file` brief asked for `symlink`/`read_link` backend primitives; `read_dir(p) -> Vec<PathBuf>` was added as a third, because `file::Absent` must tell an empty directory from a non-empty one at check time and there is no listing primitive (7.3: one method per primitive, no `ls` through `cmd`). Reverse: drop `read_dir` and make `Absent` always recursive.
- [M6] 2026-09-08 `file::Copy` builder order follows the vision 5.6 example: `Copy::from_bytes(..).to(dest)` finishes the builder and `.mode()/.owner()/.backup()` sit on the finished op (as `Directory` does), rather than before `.to`. Reverse: move the three setters onto `CopyBuilder`.
- [M6] 2026-09-08 When a `Copy` changes both content and attributes, the report shows the content diff only (`Diff` has no shape carrying both); `apply` still sets the attributes. An attributes-only change shows `Diff::Attrs` and does not rewrite the file. Reverse: add a combined `Diff` variant in the SDK.
- [M6] 2026-09-08 `file::Attrs` refuses a symbolic link instead of following it, because `stat` is `lstat` and `chmod` follows, which would make every run report a change on the link's 0777. `file::Symlink` refuses to replace a directory even with `.force(true)` (Ansible refuses too) and `.force` only covers a regular file. Reverse: use `stat_follow` in `Attrs` and allow directory replacement behind `.force`.
- [M6] 2026-09-08 `file::Block` with an empty block removes the managed block (Ansible `blockinfile state=absent`) instead of a separate `Block::Absent` type: the marker is the identity and the empty content is a natural "nothing between the markers". `plan_block` takes the first BEGIN and the first END after it; an orphan BEGIN counts as no block (Ansible takes the last of each and swaps). Reverse: add `file::BlockAbsent`.
- [M6] 2026-09-08 Observation for the SDK, not changed here: `Local::write` creates a new file at 0600 (tempfile's default) when nothing existed, so `Copy` and `Line::create(true)` without `.mode()` produce 0600 files where Ansible would give `0666 & ~umask`. The op tests cannot see it (the Fake creates 0644). Suggest `Local::write` chmod new files to 0644 or apply the umask.
- [M6-file] 2026-09-08 `Backend::remove` is single-entry (empty dir or file); `remove_all` is the only recursive delete. `rename` added for atomic replacement. New files from `Local::write` get 0666 minus umask. The fake resolves symlinks for reads and `stat_follow`; a write at a link's path replaces the link (mirrors Local). `Line`/`Block` refuse symlinked paths. Reverse: per item, see the M6-file-ops report self-review.
- [M6-sd] 2026-09-08 `systemd` state ops run both probes (`is-enabled`, `is-active`) in `check` and refuse a unit `is-enabled` reports as not found (`not-found` on systemd 253+, empty stdout with a non-zero exit before), because `is-active` answers `inactive` for a unit that does not exist and `Stopped` would otherwise be silently satisfied on a typo. Reverse: drop the `NotFound` bail in `probe_existing`.
- [M6-sd] 2026-09-08 `systemd::Disabled` refuses `generated` and `transient` units with the same message as `static`: all three have no `[Install]` section, `systemctl disable` exits 0 on them without changing anything, and the op would report `changed` on every run. `alias`, `indirect` and `linked` go through `systemctl disable` as Ansible does. Reverse: shrink `EnabledState::cannot_be_disabled` to `Static`.
- [M6-sd] 2026-09-08 `systemd::Enabled` and `systemd::Running` refuse a `masked` unit with a message naming `systemctl unmask` instead of unmasking (vision 6.7: one resource per op); `Disabled` treats `masked` as satisfied since the brief counts it as not enabled. Reverse: add an `.unmask(true)` builder.
- [M6-sd] 2026-09-08 `EnabledState::is_enabled` follows `systemctl is-enabled`'s own exit-0 table (`enabled`, `enabled-runtime`, `alias`, `static`, `indirect`, `generated`, `transient`); `linked`/`linked-runtime` count as not enabled, as systemctl exits 1 on them. Reverse: move `linked` across.
- [M6-sd] 2026-09-08 After `systemctl enable`/`disable` the op re-reads `is-enabled` and fails if the word did not flip (systemctl exits 0 with only a warning for a unit it cannot enable), so a step never reports `changed` for a no-op. Reverse: drop the two `ensure!`s in `apply`.
- [M6-sd] 2026-09-08 `Fake` was not extended with sequenced command responses; state-op apply tests use one fake for `check` and a second for `apply` because the post-apply probes share their argv with the check probes. A `with_cmd_seq` on `Fake` would make those tests single-fake; left for the lead to decide since two sibling branches already touch `fake.rs`. Reverse: n/a.
- [M6-so] 2026-09-08 `apt::Present::update_cache(bool)` became `update_cache(Duration)` (vision 6.8 writes `update_cache(Duration::from_secs(3600))`); there is no `update_cache_always()`, `Duration::ZERO` reads well enough. Reverse: re-add the bool form as a second method.
- [M6-so] 2026-09-08 The apt lists' age is read with `stat -c %Y` through `sys.cmd` (`/var/lib/apt/lists`, then `/var/cache/apt/pkgcache.bin`; unknown age counts as stale) because the SDK's `Stat` carries no mtime and the brief forbids touching the SDK; branch m6-file-ops is already editing `backend/mod.rs`, so adding a field there would conflict. - [M6-so] 2026-09-08 `apt::Latest` refreshes the cache in `apply` only (vision 6.8 places `apt-get update` in `apply`), so a `Latest` whose `check` finds every package current against stale lists reports `ok` without refreshing. Not changed; the module docs say to run `apt-get update` via `shell::Command` first when a box never refreshes on its own. **DECIDED by Cadu 2026-09-08: adopt Ansible's behaviour, refresh in `check`.** Implemented on branch `amendments`; see `[M7-amend] apt::Latest` below.
- [M6-so] 2026-09-08 All apt ops, `Present` included, refuse when `!sys.is_root()` (the brief: "all ops refuse when not root"); a non-root dry run of `apt::Present` therefore fails at `check` instead of reporting would-change. Reverse: drop the root check from `require_apt_root` for `Present`.
- [M6-so] 2026-09-08 `apt::Absent` fails on a package in a dpkg state other than installed, config-files or unknown (half-configured, unpacked, ...) instead of guessing; `dpkg --configure -a` is a human's call. Reverse: treat any known state as present.
- [M6-so] 2026-09-08 `apt::Latest` has `.install_recommends(bool)` (default off, `--no-install-recommends` on the install path) mirroring `Present`, so the two ops install the same set for a missing package. Reverse: remove the method.
- [M6-so] 2026-09-08 `hostname::Is::check` reads `/proc/sys/kernel/hostname` through `sys` and only falls back to `facts.hostname` when that file is unreadable: facts are gathered once at startup, so a second step in the same run would otherwise see the old kernel name and report `changed` twice. - [M6-so] 2026-09-08 `hostname::Is` validates the name in `check` (not in `new`, which cannot fail) and accepts dotted FQDNs up to 253 characters with 63-character labels; uppercase is allowed (`HOME-GAMES` is the brief's own example). Reverse: reject dots or fold case.
- [M6-so] 2026-09-08 `sysctl::Present` uses its own line planner (`plan_sysctl_line`) instead of `file::plan_line`: `key=value` and `key = value` must count as the same line, duplicates are collapsed onto the first occurrence, and values compare token-wise (`4096 131072 6291456` equals the kernel's tab-separated form). - [M6-so] 2026-09-08 `sysctl::Present` refuses when the drop-in's directory does not exist (vision 6.7: prerequisites are not created silently; `/etc/sysctl.d` exists on every Debian) and, with `apply_now` on, when `/proc/sys/<key>` is missing; with `.apply_now(false)` a missing key is persisted only and `previous_live` is `None`. - [M6-so] 2026-09-08 `sysctl::Present::apply` re-plans the file text from the current file instead of carrying it in the diff: `Diff::Attrs` is used so the file and live changes render as one table, and re-reading a small file is cheaper than a second diff variant. - [M6-so] 2026-09-08 `apt::Present` predicts its output only when `apt-cache policy` can name a candidate version for every missing package; otherwise the plan carries the diff with no prediction (vision 12). - [M6-so] 2026-09-08 `apt::Present::apply` installs the names carried in the diff that `check` produced (vision 6.2) and refuses a plan that names none, instead of reading them back out of the prediction; the report is rebuilt from dpkg after the install. - [REPO] 2026-09-10 The licence is **`MIT OR Apache-2.0`**, recorded here because it was inherited convention that nobody had written down — Cadu asked why there are two, which is the right question to ask of an unexplained pair. - [ISSUE-44] 2026-10-03 **The host's verdict is what the playbook returns: a step failure the playbook catches is `recovered`, not `failed`.** Decided by Cadu in session on 2026-09-27; issue #44 is the specification, and its closing comment adds the `FAILED at` block path. The manual (§14 "When a step fails") had documented the opposite as intended — "the step is still counted as failed … you can decide what to do next, not whether it happened" — because `Ctx::step` bumped `summary.failed` before returning the error, which `[REPO] 2026-09-11` (:319) recorded as an observation, not a decision. Vision §14 says ignoring is `.ok()`, rescue is `if let Err`, retry is a loop; by the repository's rule the vision wins, so this was a bug and the manual is corrected. (1) **Semantics as built.** `Ctx::step` no longer counts a failure; it records `FailedStep { id, cancelled }` in `Shared` (one list across `as_user` clones and blocks) and puts the step's id and block path on the `StepFailed` layer. When the entry returns, `runtime::classify` makes each record `failed` if its id is the one on the escaped error's `StepFailed`, or if the run was already cancelled when it failed, and `recovered` otherwise; a host that failed with no such step (`bail!`, a panic, a cancellation before any step started) still counts `failed = 1`. The host failed iff the entry returned an unabsorbed `Err`, panicked, or the channel is cancelled at the end, so `failed > 0` is exactly "the host failed", and the exit code (2 iff `failed > 0`) and both CLI verdicts (`render.rs`, `run.rs`'s `--json`) needed no change of rule. The live step line and `FAILED at` lines are unchanged: classification happens at the end because only then is it known. #47's absorption arms are untouched and absorption is neither failed nor recovered; decision (b)'s step failures follow the same rule as any step. (2) **Identification by id, never by name**: names repeat in a retry loop, so a loop that fails five times and returns the last error reads `failed=1 recovered=4`. `StepFailed::id` is private with a getter and set only by `Ctx`, so a layer a playbook builds by hand claims no recorded failure and the verdict degrades to the floor of one; counting is saturating and never subtracts. The id alone is not enough, found in review: `Ctx::new` is public and every context numbers its steps from 1, so a playbook that caught its own step 1 and returned a second context's step-1 error read `failed=1 recovered=0` naming the wrong step. Each `Shared` therefore draws a token from a process-wide atomic counter (starting at 1, so a hand-built layer's 0 is nobody's), `StepFailed` carries it beside the id, both private to the SDK, and the runtime matches on the pair (`Ctx::claims`). Rejected: a random token (needs a dependency or an entropy source for no gain over a counter) and the `Rc` pointer of `Shared` (reusable once freed). (3) **What the issue left open, decided here.** (a) A step is "cancelled" if the channel was cancelled when it failed, not only on the `not applied` path, so an op that gives up because of the cancellation is never recovered either. (b) When the host fails only because of the cancellation (the playbook swallowed every error and returned `Ok`), the runtime emits `Failed { step: None, error: "cancelled: <reason>" }`, since otherwise the recap would show `failed 1` with nothing above it saying why; when an error did escape, its own frame is the only one. (c) `Event::Failed` gains a `blocks` field beside `step`, like every step event, rather than folding the path into `step`; the closing line reads ``FAILED at [outer][inner] `boom`: …`` — the prefix as the step line prints it, the name still quoted so a colon in it stays unambiguous — and a top-level step reads exactly as before. The `not started` cancellation's layer carries the block path too, with no id. `Event::Failed` also carries the step `id`, but only when the runtime matched the error to one of this run's steps (`None` for a second context's error, a hand-built layer, a step refused before it started, a panic and the cancellation frame); `Event::failed(e, id)` takes that matched id and reads step and blocks off the layer. (e) **How the renderer pairs a `Failed` frame with a step's held-back reason.** The key is the step id, block path and name together: names repeat (a first version matched name and blocks, and `let first = ctx.step("x", ..); let second = ctx.step("x", ..); first?;` lost `second`'s reason), and ids repeat across `Ctx` values (a second version matched the id alone, and a second `Ctx::new`'s step 1 dropped this run's step-1 reason; the renderer cannot see the run token the runtime matches on). A frame with no id (a panic, `bail!`, a swallowed cancellation, another context's error) pairs with nothing, so a reason held back before it always prints. A reason that already printed, because another step began before the error was returned, is not printed a second time: the frame's line reads ``FAILED: [b] `x` (reason above)``, unless another failed step of the same name and blocks also printed, in which case "above" would be ambiguous and the reason is printed again in full; and only when the frame's chain, with the step layer dropped, is the one that printed: a `.context(..)` the playbook added on the way out was not above, and a real run found the line pointing there with the words lost (`let d = ctx.step("deploy", ..); ctx.step("report", ..)?; d.context("deploying the app")?`), so such a frame prints its chain in full. The reason always comes first: lines from outside a step that arrive while a chain is held back (the playbook's own `ctx.warn(format!("skipping: {e:#}"))`; `{e:#}` because `{e}` is only the outermost layer, `step `x``) print after it, whether the playbook caught the error or the frame prints it. The by-hand `Compact` printer still prints the frame's whole chain after `FAILED at`, layer included, as before this PR. A recovered failure's command stderr is still not shown at `-v`, which is #58.
